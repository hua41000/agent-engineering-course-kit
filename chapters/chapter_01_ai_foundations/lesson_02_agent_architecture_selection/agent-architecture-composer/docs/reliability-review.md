# 整体方案可靠性评审

[返回项目入口](../README.md)

## 1. 结论与评审边界

**结论：方向可行，方案需修改。可开展针对关键假设的验证原型，当前尚不足以证明能够稳定生成可靠的架构方案。**

共享内核、结构化事实、当前/目标分离、框架数据版本化、课程级产品与 Skill 分开归属，这些设计可以保留。主要缺口集中在架构组合的语义校验、无可行解的表达，以及推荐有效性的独立验收。

本次发现 3 项 P1 和 4 项 P2。P1 表示会影响核心选型正确性或发布结论的设计缺口；P2 表示在特定输入、续填或宿主环境中影响可靠性的缺口。全部为文档评审发现，尚未对运行程序复现故障。产品没有实现，不能把下文情景推演视为真实测试结果。

评审范围为四份方案、README 与 manifest，并核对根测试职责、Agent Skills 官方权限说明及浏览器文件存储边界。采用 `review-code` 的需求、架构、契约、安全和验收维度；报告随本产品管理，不另建根级 Feature 包。本次只增加评审记录与入口，不修改四份被评审方案。

## 2. 按优先级排列的发现

### R1 · P1：缺少架构组合与校验的明确中间模型

**位置**：[技术方案](technical-design.md) 第 93、115、162—169、219 行；[方法设计](methodology.md) 第 139 行。

**问题**：Stage 当前只有依赖、输入输出、事实与控制能力；`compose` 被描述为生成当前/目标/备选结构，图表则假定存在“已验证的 Architecture IR”。方案未定义这个 IR 的结构、组合约束与校验者。七/十项移交契约仍主要以文字清单存在。

**触发场景**：调查、审批和写入三个阶段分别命中正确模式，但写入节点绑定到错误租户，审批对象与执行参数不一致，或者恢复路径绕过审批。单阶段前提都满足，整体仍无法成立。另一个场景是调查结果要求返回早期计划阶段；只有阶段 DAG 与内部循环的描述，尚不明确如何表达这种组合。

**影响**：实现者容易将命中模式拼成图，无法保证报告、图和迁移计划表达同一个可行结构。共享内核可以让两端生成同样的错误组合。

**建议**：在编写组合器前定义 `ArchitecturePlan`、分层子图、节点角色、带条件的边、控制权转移、状态所有者、能力绑定、权限范围与预算。至少校验：每阶段有完成谓词与责任人；每次移交有返回/接管语义；执行节点的权限要求不能被任何路径跳过；共享状态和并行合并相容；循环有退出与预算。这里校验的是方案内部一致性，不能宣称已证明目标系统运行安全。

**关闭条件**：同一输入生成 IR、报告和图；至少三个“局部成立但全局冲突”的反例被结构校验拒绝或降级，跨阶段回退有明确表达。

### R2 · P1：缺少“无可行方案”和“已改变业务范围”的独立结果

**位置**：[方法设计](methodology.md) 第 83、102、151—155 行；[技术方案](technical-design.md) 第 101、130、179 行。

**问题**：Decision 只有证据程度的三个状态。文档要求区分不可实施与未被证明，但没有对应的数据契约。当写入能力不满足时直接退到 `proposal_only`；当语言、部署、许可等约束排除全部候选时，也没有明确空候选行为。

**触发场景**：业务明确要求在规定时间内自动完成一次动作，人工建议无法满足目标；控制条件又不允许自动执行。当前规则可返回“只生成建议”，这改变了业务终态。另一个例子是所有已知框架都不满足部署和许可硬约束，却仍有“1 个当前推荐”的输出要求。

**影响**：收窄范围的替代方案可能被展示为满足原任务的当前方案；完整报告掩盖了目标尚未满足。

**建议**：分开 `feasibility`、`evidence_level` 和 `goal_coverage`。可行性至少支持 `feasible/conditional/infeasible/insufficient_information/out_of_scope`；无可行解列出互相冲突的约束与可协商项。范围收缩要记录 `scope_delta`，用户接受后才能作为新的目标；此前只显示替代提案。

**关闭条件**：空候选、互斥硬约束、超出知识库范围、降为只读不满足原终态四类输入有不同且可解释的输出；不自动放宽硬约束。

### R3 · P1：选型建议有效性仍待验收

**位置**：[技术方案](technical-design.md) 第 239—251 行；[交付管理](delivery-management.md) 第 115—120 行。

**问题**：已有规则回归、反例与双端一致性测试，但案例来源、独立评判程序和发布阈值尚未定义。通过“应命中某规则”只能证明实现符合该规则；课程九场景若同时用于编写规则与评分，会留下方法正确性盲区。

**触发场景**：两端对所有课堂案例输出一致、规则追踪完整；面对陌生行业的复合任务，仍持续过度推荐 Autonomous 或多 Agent。当前验收没有明确办法判定这种系统性偏差。

**影响**：可能在工程测试通过后把未经校准的选型建议作为课程工具发布。原先根 `npm test` 仅检查 `getProjectSummary()`，与本产品可靠性无关。

**建议**：在完整开发前建立独立评估集，涵盖规则编写未使用的项目、简单反例、矛盾、未知、存量系统和复合任务。至少由课程负责人和另一位工程评审者独立标注允许方案、禁止结论、必要追问与理由，分歧保留并裁决。通过真实学员试用检查“输入业务描述 → 标准化事实 → 报告”的完整链条。

**关闭条件**：先确定再执行发布门槛：门禁反例零违规、关键未知不冒充已知、推荐可接受性、无依据结论、关键事实采集准确性/遗漏和答题负担分别计量。除明确不变量外，数值阈值应在先导试用后由负责人冻结，当前不编造通过率。小样本通过仍需注明适用范围。

### R4 · P2：部分模式触发条件无法区分确定性反馈与自主决策

**位置**：[产品需求](prd.md) 第 84—85 行；[方法设计](methodology.md) 第 119 行。

**问题**：P-07 以“新观察持续改变下一步”触发 ReAct，但确定性状态机也可以据观察选择下一步。文档同时说硬约束优先，却没有把这类经验线索与足以成立的模式条件区分清楚。

**触发场景**：固定重试策略根据 HTTP 200/429/失败结果执行下一步。它符合观察改变动作的描述，路径与选择规则又完全可枚举；不同实现者可能选择 ReAct、Workflow 或同时保留，却没有规则级裁决依据。

**影响**：在本来适合普通代码的任务中增加模型决策；问卷即使准确填写也可能得出过度复杂的建议。

**建议**：P-07 增加“运行时选择策略无法在可接受成本内预定义”和“模型语义判断具有待验证收益”等前提；确定性选择足够时保留基线。所有模式规则分开必要条件、支持性线索、反例与复杂度收益，避免将经验线索直接当作必选条件。

**关闭条件**：固定重试、有限路由和开放调查三个相邻案例的触发/排除理由清晰；其他模式按相同标准检查边界。

### R5 · P2：证据等级尚缺提升、失效与环境匹配规则

**位置**：[技术方案](technical-design.md) 第 94—103 行；[产品需求](prd.md) 第 99、145 行。

**问题**：已经区分用户声明、代码、文档与运行证据，也保存哈希，但 `present_verified` 和 `evidence_supported` 的产生条件未定义。未规定证据对应哪个环境、租户/配置、测试范围，以及代码或约束变化后何时失效。

**触发场景**：用户确认“审批已验证”，实际只有过往开发环境的一次测试；生产配置和权限模型不同。或者 Skill 发现测试代码与历史通过记录，直接认为当前写入控制已经验证。

**影响**：证据身份虽然有字段，推荐仍可能获得超出证据适用范围的等级。

**建议**：证据声明与系统评定分开；定义校验者、环境、时间、配置/代码版本、覆盖范围和失效条件。用户确认只能确认其陈述，不能自动升级为实际运行证明。报告按主张显示证据程度，避免某一阶段有证据就提升整个方案等级。

**关闭条件**：用户自报、过期运行证据、环境不匹配、局部验证四类输入不会升级为全局证据支持；变更能使受影响证据失效。

### R6 · P2：Session 无法从 Decision 无损恢复问答历史

**位置**：[产品需求](prd.md) 第 103、143 行；[技术方案](technical-design.md) 第 91、117、177、223 行。

**问题**：PRD 要求旧回答保留、失效不复活，技术方案要求拒答不重复询问；但又规定六类文件均从 Decision 生成。Decision 保存事实快照与结果，不包含完整的原始回答、已问/拒答记录、失效原因和分支关系，Session 表也没有这些字段。

**触发场景**：用户拒答一个问题，或先打开预算写入再关闭，导出后交给 Skill 续填。当前事实快照无法区分“从未问过”与“已经拒答”，也无法恢复失效答案为何失效。

**影响**：续填时重复追问、恢复旧答案，或者在 Web/Skill 切换后产生不同结果。

**建议**：明确 Session 是原始回答、确认/拒答、revision、失效依赖及分支的权威源；Decision 引用某个 Session revision。`exportSession(session)` 与 `renderDecision(decision)` 分开，导出包可同时携带二者，检查引用一致性。

**关闭条件**：拒答、修改上游回答、失效下游答案及分支四类会话跨端导入后，待问问题、有效事实和最终决策保持预期一致。

### R7 · P2：Skill 的采集限制尚未落实到宿主执行边界

**位置**：[技术方案](technical-design.md) 第 191—195、210 行。

**问题**：方案要求不读敏感文件、不越出根目录、不执行目标脚本，但当前主要是 Skill 流程约束；未说明各受支持宿主如何限制文件和执行工具，也未说明当这些限制无法强制实施时对用户承诺到什么程度。

**触发场景**：宿主拥有任意文件读取和 shell 权限，模型在调用专属采集脚本之外直接读取文件。采集脚本自身的路径校验覆盖不了其他工具。

**影响**：用户可能把“只读采集”的产品说明理解为工具层隔离保证。格式兼容和正常用例通过无法证明拒绝读取与拒绝执行行为。

**建议**：兼容矩阵分别记录文件读取限制、命令执行限制和模型数据传输边界。强隔离模式使用宿主沙箱/白名单工具，或让 Skill 只分析预先生成的受限上下文包；普通模式明确约束属于操作规范。不能依靠提示词或 `allowed-tools` 字段宣称普适强隔离。

**关闭条件**：每个承诺支持的宿主都有对应能力说明和越界拒绝用例；不能强制隔离的宿主使用明确标注的模式，不作相同保证。

外部依据：Agent Skills 的 [格式规范](https://agentskills.io/specification)将 `allowed-tools` 标为实验能力，并说明各实现支持可能不同；[宿主集成说明](https://agentskills.io/client-implementation/adding-skills-support)将文件权限处理放在宿主权限系统中。上述限制结论属于据此结合本方案做出的工程判断，访问日期为 2026-09-22。

## 4. 已合理处理的部分

- 规则内核采用固定输入、知识版本和评估日期，可作为双端计算一致性的基础。
- 明确保留传统软件、LLM Feature、维持现状和信息不足，避免一律推荐复杂 Agent。
- 把框架支持状态、成熟度、版本和来源分开，并要求过期时降低结论强度。
- 自研薄 Harness 与现有框架都有维护代价，课程 DataAgent 没有成为全部项目的硬编码答案。
- 可安装 Skill 通过构建携带内核与知识快照，避免运行时依赖课程仓库路径。
- 文档归属、稳定文件名、manifest 和派生产物分离符合当前仓库管理规则。
- 已考虑 `file://` 保存差异，并提供 JSON 导入导出退路；这项方向与 [MDN 的 localStorage 说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)一致。仍需实测目标浏览器，但当前无需将其列为新的设计阻断项。

## 5. 建议的修订与验证顺序

1. **先补齐决策契约**：R1/R2/R4/R5；选三个代表案例手工走完“回答 → 事实 → 规则 → 全局方案 → 报告”，明确不足以自动判断时的退出。
2. **同步建立独立评估方式**：R3；案例标注在调规则前完成，留出保留集。建议先做 12—20 个完整案例的先导评估，数量是项目建议，不代表统计充分性。
3. **用最小双端贯通原型验证假设**：至少完成一个 Web 问答、一个 Skill 项目采集与同一内核的报告；覆盖 R6/R7。无需等完整 Web 和全框架库完成后才测试宿主。
4. **再扩充课程方法和候选库**：完整方法覆盖仍是首版发布目标；实现顺序可以从少量可解释案例扩展。依据实际案例和宿主工作量重估排期。

现有“13 个开发日”只能作为初始工作量假设。R1—R7 的修订、独立标注和学员试用尚未被任务表完整计入，不宜直接作为可靠版本的交付承诺。当前也没有依据给出新的精确工期。
