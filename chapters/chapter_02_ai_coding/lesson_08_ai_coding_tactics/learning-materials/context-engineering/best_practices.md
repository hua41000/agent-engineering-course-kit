以下整理为 **10 条最佳实践**。工具机制核对截至 **2026 年 10 月 15 日**；GoodCase、BadCase 是依据研究结论构造的企业研发示例，并非原作者案例的直接转述。

### 最佳实践 A：

- **标题：AGENTS.md 做好入口导航**

- **描述：**

  在 AGENTS.md 保留项目约束、验证命令和资料入口，详细知识按需读取，并根据真实失败案例持续更新规则。

- **GoodCase：**

  根目录 `AGENTS.md` 只保留这样的信息：

  > 所有业务接口必须经过 `src/authz/` 的统一授权入口。
  > 涉及租户数据访问时，先读 `docs/security/tenant-isolation.md`。
  > 修改异步任务时，先读 `docs/architecture/job-lifecycle.md`，其中解释了为什么不能在请求线程里直接执行。
  > 提交前运行 `make check`；修改数据库结构还需运行迁移兼容性测试。

  详细架构不重复抄写；代码格式规则交给 lint。某条规则对应的问题不再存在时，及时删除或更新。

- **BadCase：**

  让 AI 自动扫描仓库，生成两千行的 `AGENTS.md`：完整目录树、每个模块的介绍、通用 Clean Code 原则、历史决策和所有工具教程都放进去。以后每次出错再追加一条“必须”，从不检查冲突、过期信息或实际收益。

- **参考依据：**

  OpenAI 用约 100 行的入口文件引导按需读取；行数只是一项实践记录。优先保留高频、全局、容易误判的信息，如关键约束、非显然的设计原因与特殊陷阱，避免复述目录、通用常识和 README。实证研究未发现增加上下文文件就能普遍提高成功率，规则应按实际收益增删。 [OpenAI](https://openai.com/index/harness-engineering/) · [arXiv](https://arxiv.org/html/2602.11988v3)

### 最佳实践 B：

- **标题：按作用域管理记忆**

- **描述：**

  把团队规则、个人偏好和临时任务状态分别放到对应位置，先审查经验的证据与适用范围，再决定是否长期保留。

- **GoodCase：**

  团队认可的“金额使用最小货币单位存储”进入项目规则；个人的“方案先给取舍结论，再展开细节”进入用户级偏好；“本次退款接口的重试上限尚待确认”只写入任务记录。

  使用 Claude Code 时，跨项目偏好可放在 `~/.claude/CLAUDE.md`，项目内私有偏好可放在加入 `.gitignore` 的 `CLAUDE.local.md`。自动记忆先定期审阅，确认适用范围和事实依据后，再决定是否提升为团队规则。

  内容少时不必过度拆分；内容增长后，再采用“短索引＋按主题读取的文件”。

- **BadCase：**

  把“我偏好 PostgreSQL”“这个老项目暂时不能升级数据库”“昨天为了排错关闭了一项检查”“退款模块尚未完成”混写进一个共享 `memory.md`，并要求所有任务默认读取。AI 一次误判产生的“经验”，也未经审查直接提交到团队仓库。

- **参考依据：**

  Claude Code 区分团队、用户、项目内个人指令和自动记忆；它们提供不同作用域的上下文，不能保证模型永久遵守。Vercel 将观察、建议与已接受规则分开，审查后再沉淀到指导文件、示例或检查；个人偏好与临时结论不应直接升级成团队规范。 [Claude](https://code.claude.com/docs/en/memory) · [Vercel](https://vercel.com/blog/teaching-agents-product-design-at-vercel)

### 最佳实践 C：

- **标题：确认上下文确实读到了**

- **描述：**

  区分启动注入、条件加载、按需检索和手动引用，检查实际读取记录，并在工具升级后验证关键规则能否触发。

- **GoodCase：**

  在 monorepo 中，让前端规则只匹配前端路径，让数据库迁移规则只在相关任务中应用。开始一个高风险任务时，检查已加载规则、实际文件读取记录以及资料访问是否成功；对必须遵守的接口契约，在任务中明确要求先读取。

  更换工具或升级版本后，用一个小任务验证规则是否仍然按预期触发。

- **BadCase：**

  把一个长 `CLAUDE.md` 拆成十个 `@` 导入文件，就认为完成了按需加载；在仓库里创建 `context/` 后，就默认 AI 会自动读取；装了 MCP、放了链接，就认为相关资料已经进入了当前上下文。

- **参考依据：**

  Codex 启动时从项目根目录到当前工作目录构建指令链，项目指令默认合并上限为 32 KiB，不能假定所有嵌套 AGENTS.md 都已加载。Claude Code 的 @ 导入启动时展开，拆文件不会减少占用；AGENTS.md 支持受版本、已有指令及配置影响，可用 /context 检查。Cursor 规则支持常驻、文件匹配、相关性判断或手动应用，规则中的 @文件 是按需引用。 [ChatGPT Learn](https://learn.chatgpt.com/docs/agent-configuration/agents-md) · [Claude](https://code.claude.com/docs/en/memory) · [Cursor](https://cursor.com/docs/rules)

### 最佳实践 D：

- **标题：引用资料时说明用途**

- **描述：**

  引用关键资料时注明需求、契约、参考实现或背景等用途，同时给出适用范围与可验证的目标，帮助 AI 正确取舍。

- **GoodCase：**

  > 为现有订单服务增加部分退款。
  > 先读 `specs/142-refund/spec.md` 和 `context/142-refund/api-contract.md`，它们分别是已确认需求和外部接口约束。
  > 参考 `src/payments/capture.py` 的鉴权、幂等和错误处理方式，但不要照搬支付状态机。随后自行检索受影响的调用方。
  > 本次不做人工审批后台。先列出资料冲突和待确认项，再给实现计划。
  > 验收必须覆盖重复请求、累计退款超额和跨租户访问；先运行现有支付测试建立基线。

- **BadCase：**

  > 参考这些文件，把退款做完整，要符合企业级最佳实践。

  同时附上旧 PRD、新 PRD、全量接口文档和三个不同模块的实现，却不说明哪个版本有效、哪些行为可以复用、哪些只是历史背景。

- **参考依据：**

  Cursor 建议明确引用已知关键文件，让 Agent 搜索未知依赖，并避免大量无关附件。Claude Code 建议提供可执行测试、截图或预期输出，让 Agent 检查自己的工作；资料角色和验证目标应比“完整、可靠、企业级”等抽象要求更具体。 [Cursor](https://cursor.com/blog/agent-best-practices) · [Claude](https://code.claude.com/docs/en/best-practices)

### 最佳实践 E：

- **标题：开工前准备 context 资料包**

- **描述：**

  围绕本次变更收集必需证据，标明来源、版本、用途和确认状态，用资料索引引导 AI 先读关键内容再开展工作。

- **GoodCase：**

  开发退款需求前，准备：

  ```text
  context/142-refund/
    README.md                  # 资料索引、必读项、来源、版本、确认状态
    payment-api-v3.md           # 本次相关的官方接口章节
    samples/success.json       # 脱敏后的真实响应样例
    samples/duplicate.json     # 重复请求或回调的样例
    design/README.md            # 精确设计节点、相关状态截图及说明
    reproduction.md            # 现有缺陷的复现步骤与证据
  ```

  `README.md` 引用已评审的 `specs/142-refund/spec.md`，并指明应参考的现有代码路径。可共享、需要复现的资料纳入版本管理；临时下载、大型日志和个人草稿放入忽略目录，敏感数据先脱敏。

  在任务提示中明确“先读这个索引”，确保读取入口清楚。

- **BadCase：**

  只提供一句“接入退款”，让 AI 自己生成需求文档、接口协议、响应 JSON 和测试用例，再用这些互相一致的生成物证明实现正确。文件看似齐全，但关键业务事实没有真实来源。

- **参考依据：**

  Armin Ronacher 会预先获取精选资料，放入 Git 忽略目录后在任务中引用；Cole Medin 的公开实践也强调功能描述、示例、文档和特殊注意事项。资料包应区分原始证据、已确认结论和待验证假设，已有权威文档直接引用，避免维护易分叉的副本。 [Armin Ronacher's Thoughts and Writings](https://lucumr.pocoo.org/2025/7/30/things-that-didnt-work/)

### 最佳实践 F：

- **标题：接口资料先对齐版本**

- **描述：**

  先确认依赖与协议的实际版本，再提供适用的官方契约及成功、失败样例，让实现和契约测试依据同一组事实展开。

- **GoodCase：**

  接入支付服务前，先读取依赖锁文件和接口版本声明，再获取认证、幂等、回调验签、错误码与重试规则的相关章节。

  同时提供脱敏的成功、失败、重复回调样例，明确金额单位、可空字段、时间格式和状态转换。要求 AI 根据官方约束和这些样例编写契约测试；文档与真实响应不一致时，记录差异并确认，不自行猜测兼容逻辑。

- **BadCase：**

  项目使用旧版 SDK，却让 AI 根据最新版文档生成代码；模型不确定字段含义时自己补一个 JSON 样例；测试只验证返回 `200`，没有提供错误响应、重试行为或回调样例。

- **参考依据：**

  Vercel 的 Next.js 专项评测中有 56% 案例未触发文档 Skill，版本匹配的精简文档索引在该实验中更有效；这不能推广为所有任务都应放弃 Skill。资料存在、可检索和实际读取需分别确认。Context7 可辅助获取版本化文档，仍需核对返回资料与锁文件、SDK、API 协议版本是否匹配。 [Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals) · [Context7](https://context7.com/docs/overview)

### 最佳实践 G：

- **标题：设计上下文补齐结构与状态**

- **描述：**

  实现界面时同时提供目标节点、截图、现有组件和交互状态，复用项目规范，并通过实际渲染核对各状态的视觉与行为。

- **GoodCase：**

  实现退款管理页时，提供精确 Frame 或节点，便于定位目标设计。先用 `get_design_context` 和 `get_screenshot` 获取目标设计，再关联项目现有的 `Table`、`MoneyInput`、权限组件和设计令牌。

  资料中另外注明加载中、空数据、接口失败、无权限、退款处理中等状态，以及分页、筛选、校验行为。完成后在浏览器实际渲染，与对应状态截图进行对照。

- **BadCase：**

  给一张静态截图，让 AI“像素级还原”；没有说明字体、组件库、响应式规则和异常状态。AI 重新造了一套按钮、表格和样式，页面初看相似，却不符合现有产品的交互与组件规范。

- **参考依据：**

  Figma 将截图的视觉信息与组件、变量、布局、代码映射等结构信息区分；Code Connect 可关联真实组件。官方 MCP 指南建议同时获取设计上下文和截图，响应过大时定位子节点分段获取；生成的 React/Tailwind 表达作为设计参考，仍须遵循项目技术栈。 [Figma](https://www.figma.com/blog/introducing-figma-mcp-server/) · [GitHub](https://github.com/figma/mcp-server-guide)

### 最佳实践 H：

- **标题：SDD 按阶段交接上下文**

- **描述：**

  在需求、研究、方案和实施之间交付已经审查的事实与决策，发现条件变化时同步修订方案、任务和验收预期。

- **GoodCase：**

  开发企业异步导出功能时：

  需求阶段确认租户边界、权限、导出规模和验收条件；研究阶段查清已有任务队列、对象存储封装及下载鉴权，并附代码位置；方案阶段明确任务状态、接口契约、失败恢复和验证办法；开发任务只引用自己需要的那部分资料。

  若开发时发现对象存储能力不满足原方案，先提出变更并同步更新方案、任务和测试预期，再继续实现。

- **BadCase：**

  AI 一次生成几十页方案，未经检查就继续拆任务、写代码。中途发现事实不符，直接修改实现，但规格和验收用例仍沿用旧假设。最后“按方案全部完成”，实际上需求、文档、代码和测试描述的是四个不同系统。

- **参考依据：**

  HumanLayer 的 Research → Plan → Implement 先查清当前实现和约束，再审方案；前置设计审查仍需配合实现后的代码审查。Spec Kit 将规范、研究、模型、契约、计划和任务衔接起来，流程规模应匹配变更，小修复无需同等文档负担；下一阶段应接收已确认事实与决策。 [LinearB](https://linearb.io/dev-interrupted/podcast/dex-horthy-humanlayer-rpi-methodology-ralph-loop) · [GitHub](https://github.com/github/spec-kit/blob/main/spec-driven.md)

### 最佳实践 I：

- **标题：探索噪声留在独立上下文**

- **描述：**

  把大量搜索、日志分析等探索交给按需检索或独立上下文，让主会话接收带证据的结论，并回读关键依据后再决策。

- **GoodCase：**

  主 Agent 准备修复重复退款问题，将调查交给独立上下文：

  > 只调查退款重试链路，不修改代码。
  > 查找入口、重试调度、幂等判断和回调处理；日志查询限定相关时间窗口与 trace。
  > 返回调用关系、关键证据的文件与行号、已确认问题、仍不确定的假设。不要返回全量搜索结果。

  原始资料保留在可访问的位置，主 Agent 对关键结论回读证据，再决定如何修改。

- **BadCase：**

  把几万行日志、全库表结构、全部搜索命中和 MCP 原始 JSON 直接灌进主会话，再要求 AI“综合分析”。或者使用继承完整历史的 fork，却误以为已经清除了之前的错误假设和无关上下文。

- **参考依据：**

  Anthropic 建议保留路径和线索、按需读取详细信息，用子 Agent 过滤探索结果。隔离效果取决于真实机制：当前 Claude Code 非 fork 子 Agent 使用新上下文，fork 会继承主会话；委派时应明确必要约束，创建子 Agent 本身无法保证已有噪声被隔离。 [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · [Claude](https://code.claude.com/docs/en/sub-agents)

### 最佳实践 J：

- **标题：跨会话留下可验证的交接**

- **描述：**

  在阶段完成、方案大改或持续纠错无效时，记录当前事实、工作区状态、验证结果和下一步，让新会话核验后继续推进。

- **GoodCase：**

  结束阶段前生成 `handoff.md`，包括：

  > **目标与边界：**当前需求版本、已确认范围、不做什么。
  > **关键决策：**采用的方案及对应规格、ADR 或证据位置。
  > **工作区状态：**分支、提交、未提交变更和重要文件。
  > **验证情况：**实际运行的命令与结果；未运行的测试及原因。
  > **未完成事项：**阻塞、失败、待确认假设和下一步必读资料。

  新会话先对照 Git 状态、实际代码和相关测试核验，再继续工作；不会因为交接记录写着“已完成”，就自动把它当成事实。

- **BadCase：**

  在一个会话里反复说“继续”“还是不对”“再修一下”，直到自动压缩。恢复后，AI 不知道哪些文件已经修改、哪些测试真正运行过、哪些方案已经作废，只能根据残缺摘要重新推断，重复之前的错误。

- **参考依据：**

  Anthropic 的长任务实验采用进度文件、Git 历史、增量任务和验证记录，仅靠上下文压缩不足以可靠恢复进展。Dex Horthy 强调将阶段成果压缩成精炼产物再进入后续阶段。交接需写清当前哪些事实成立、证据在哪里、接下来做什么；自动摘要无法保证保留全部信息。 [Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
