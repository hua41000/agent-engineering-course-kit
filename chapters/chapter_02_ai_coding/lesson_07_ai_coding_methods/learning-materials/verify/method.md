# Verify：识别错、漏、假、慢

把失败模式转成可执行的验证约束，让每个交付结论都有当前有效的证据。

四类问题可以交叠：漏验下载内容属于“漏”，同时宣称导出完全正确又构成“假”。“假”指假通过，不推断执行者意图。未标注公开来源的业务示例均为教学示意。

## 01 错

验收判据或测法有问题，可能把错误实现判对，也可能把正确实现判错。

### 判据误读

将模糊需求自行解释为确定标准，实现和测试都沿用这个未经确认的解释。

```text
需求：导出当前筛选结果
数据：共匹配 230 条，当前页显示 20 条
实现与测试：都按 20 条验收
业务预期：导出全部 230 条匹配记录
```

### 同源自证

实现和测试共享未经验证的假设，或直接用被测逻辑计算预期结果。

```text
实现：actual = calculate_total(order)
测试：expected = calculate_total(order)
断言：actual == expected → 通过
问题：计价规则错了，两边依然一致
```

### 用例失真

测试数据、前提、Mock 或断言缺乏区分能力，错误实现也能通过。

```text
目标：验证租户 A 只能看自己的订单
数据：测试库里只有租户 A 的订单
改坏实现：删掉 tenant_id 过滤条件
测试结果：仍然通过，隔离缺陷未被发现
```

### 约束臆造

把未被要求的实现细节当成业务契约，导致合理实现被误判为失败。

```text
需求：返回正确的订单汇总，不限制查询次数
测试：规定内部查询函数必须调用 2 次
优化：合并为 1 次批量查询，业务结果正确
测试结果：失败，诱导开发者撤回合理优化
```

来源旁证：[Meta · Just-in-Time Catching Test Generation，Table 2](https://arxiv.org/html/2601.22832v1) 将错误 Mock、数据提供器以及绑定内部调用次数、键值顺序的断言列为误报模式。上面的订单汇总为教学示例。

### 标准漂移

为让当前实现通过，逐步放宽断言、阈值或测试范围，使验证偏离原标准。

```text
验收要求：应导出 100 条订单
实际结果：只有 99 条
原断言：count == 100 → 失败
改后断言：count > 0 → 通过，缺失仍在
```

来源旁证：[Spotify · Honk, Part 3](https://engineering.atspotify.com/2025/12/feedback-loops-background-coding-agents-part-3) 记录了 Agent 越出任务范围、禁用不稳定测试的行为；团队增加了对原始请求与实际 Diff 的审查。上面的数量断言为教学示例。

## 02 漏

该验证的没有完整验证，缺口可能出现在场景、链路、执行或变更后的回归。

### 漏场景

只设计正常路径，遗漏角色、状态、边界或故障条件。

```text
已测：首次提交订单成功
未测：重复提交是否重复扣款
未测：超时重试是否创建重复订单
未测：提交后撤权，后续操作是否仍被允许
```

### 漏链路

模块分别有测试，实际入口、接入配置和跨模块数据传递仍缺验证。

```text
已测：导出函数正确生成文件
已测：消费者正确处理队列消息
未测：创建导出任务后，消息进入哪条队列
结果：消息发错队列，任务始终未被执行
```

公开案例：[Anthropic · Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) 中，`PUT /frames/reorder` 排在 `/{frame_id}` 路由之后，`reorder` 被按整数 ID 解析并返回 422；运行中应用的 evaluator 发现了这个入口问题。原文未说明所有单测均已通过。

### 漏执行

计划中有用例，但没有实际运行、未被框架收集，或在交接中被遗忘。

```text
计划：12 个业务验收用例
实际：只执行了 8 个
其余：4 个在子任务交接后没有继续执行
缺口：测试文件仍在，验收结果却不完整
```

### 漏回归

修复或后续修改使已有证据失效，受影响行为没有重新验证。

```text
上午：订单下载业务验收通过
下午：修改公共鉴权中间件
本轮：只跑中间件单元测试
缺口：下载接口受影响，仍引用上午的结果
```

## 03 假

用不足或不适用的证据支撑过大的通过结论，让未被证明的行为看起来已经成立。

### 执行冒充

把计划、命令发起、脚本生成或任务派发，当成执行完成。

```text
动作：启动测试子 Agent
状态：测试进程尚未结束，子任务没有回传
报告：全部测试通过，可以交付
实际证据：只证明验证任务已经发起
```

### 替身冒充

将 Mock、桩服务或简化环境中的结果，扩大为真实业务链路的通过结论。

```text
测试：Mock 订单写入接口，固定返回成功
观察：页面显示“保存成功”
报告：数据库持久化正确
缺口：未写入真实数据库，也没有重新读取
```

### 旧证据冒充

引用旧代码、另一分支、另一配置或另一个运行实例的结果，证明当前交付。

```text
工作区：下载鉴权代码已修改
浏览器：仍连接修改前启动的旧服务
报告：当前修复已经验证通过
缺口：结果无法对应本次提交与运行配置
```

### 局部冒充整体

只验证中间状态，就宣称最终业务目标已经达成。

```text
请求：创建订单导出任务
响应：202 Accepted，返回 task_id
报告：导出成功，文件内容正确
缺口：未等任务完成，也未下载和解析文件
```

## 04 慢

验证投入持续增加，却没有高效获得新证据，存在可避免的重复、等待与无效循环。

### 重复准备

每轮重新研究启动方式、安装依赖或准备相同数据，没有复用已验证的入口。

```text
Agent A：研究启动流程，准备测试账号
Agent B：再次摸索同一环境，重建同一数据
Agent C：又安装一遍依赖，重新配置端口
结果：准备工作重复，业务验证迟迟未开始
```

### 全量滥跑

不区分反馈阶段，小改动也反复触发最昂贵的完整验证，局部错误反馈很晚。

```text
修改：一个参数校验条件
每一轮：重跑全站浏览器测试与完整 CI
反馈：很久后才发现同一个局部边界错误
浪费：本可先用最小相关测试快速定位
```

公开实践：[Stripe · Minions, Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2) 先在本地取得 lint 反馈，再进入 CI；第二次推送与 CI 运行后交给人工检查。次数是 Stripe 的具体选择，项目应按风险与反馈成本确定自己的边界。

### 盲目重试

未识别失败来源，就猜测性改代码、增加等待或重复执行，没有新增定位证据。

```text
失败：连接被拒绝
实际原因：目标服务没有启动
Agent：改业务逻辑 → 增加等待 → 再跑一次
结果：同样失败，业务代码还被引入无关修改
```

### 编排内耗

多个 Agent 重复检查、共享可变资源或循环互审，互相制造失败且无法收敛。

```text
共享资源：同一个测试账号
Agent A：撤销该账号权限，验证拒绝访问
Agent B：同时验证该账号正常下载
结果：B 被 A 的操作干扰，两边反复修复重跑
```

## 05 治理方案

my-ai-infra 将全流程治理收敛为三个核心点：统一验收标准、独立业务验证、证据驱动交付。

### 统一验收标准

需求、设计、开发和测试按[共享阶段契约](https://github.com/shanggqm/my-ai-infra/blob/9c436d2ad920d9711f05776ea79b84b5cfd2c859/assets/skills/my-create-feature/references/stage-contracts.md)引用同一份有效验收条件，测试预期来自已确认的业务规则，防止需求误读、同源自证和标准漂移。

> 预期结果以需求和已确认业务规则为依据，不调用被测实现计算期望。实现行为用于识别差异，不因实现现状降低验收条件。

原文：[my-create-test-plan · 需求依据](https://github.com/shanggqm/my-ai-infra/blob/9c436d2ad920d9711f05776ea79b84b5cfd2c859/assets/skills/my-create-test-plan/SKILL.md)。

### 独立业务验证

测试 Skill 按[独立委派约定](https://github.com/shanggqm/my-ai-infra/blob/9c436d2ad920d9711f05776ea79b84b5cfd2c859/assets/skills/my-create-test-plan/references/delegation.md)从原始需求出发，检查用户路径、异常和权限边界并观察最终业务结果，防止漏场景、漏链路和局部通过冒充整体。

> 核对已有测试是否覆盖当前需求和版本；测试存在、旧报告通过或只有 Mock 的局部验证，均不能证明当前真实业务链路已通过。开发测试缺失时列具体补测项，交实施流程处理。

原文：[my-create-test-plan · 业务覆盖](https://github.com/shanggqm/my-ai-infra/blob/9c436d2ad920d9711f05776ea79b84b5cfd2c859/assets/skills/my-create-test-plan/SKILL.md)。

### 证据驱动交付

主 Agent 回收实际结果，核对代码与环境基线，变更后重验受影响范围，最终以全部承诺和集成的有效证据决定是否交付，保留失败、未执行和受阻状态。

> 已有证据核对其输入与代码基线，结果分已执行通过/失败/未执行/受阻/待核验。阶段测试只支持当前切片；最终核对全部承诺和集成。必要条件未验证、测试失败或有效评审阻塞时不结项，不降低 AC。不把文档、工具启动、文件检查或静态关键词当作实际宿主行为通过。

原文：[共享阶段契约 · 证据与风险](https://github.com/shanggqm/my-ai-infra/blob/9c436d2ad920d9711f05776ea79b84b5cfd2c859/assets/skills/my-create-feature/references/stage-contracts.md)。
