1. 流程裁剪：判断什么时候该重，什么时候该轻
   要深挖的是如何决定本次任务需要多少 SDD。
   公开实践已经出现明显分歧：Prezi 的四团队工作坊既认可结构化决策，也反馈了小任务流程过重、文档过量的问题；Instil 的工程师则报告，在自己的尝试中，完整 SDD 没有带来相称的输出改善，却增加了成本和文档漂移。这些经验不能证明 SDD 普遍有效或无效，但足以提醒我们：流程的收益依赖任务条件。Medium
   需要持续研究的，是任务规模之外的几个变量：需求清晰度、错误代价、变更可逆性、验证难度、协作范围，以及未来维护频率。
   例如，修改按钮文案，可以直接实现并验证；修改租户权限，即使只有十行代码，也值得明确安全边界和反例；探索一个尚未确定的交互方案，则可能应该先做原型，而不是先写详细规范。
   **实践重点：**逐渐形成自己的任务分流规则，区分“直接修改”“轻量规范”“完整 SDD”“先探索再进入 SDD”。不要以所有需求都走完整流程为目标。
2. 规范表达：掌握“最小充分”，而不是“尽可能详细”
   要深挖的，是规范的约束力与实现自由度之间的平衡。
   需要判断：哪些内容必须精确到没有歧义，哪些应该保留给实现阶段决定，哪些只是尚未证实的假设。尤其要避免把现状事实、目标要求、技术决策和待验证假设混写成同一种确定语气。
   OpenAI 在自己的工程实践中强调：严格约束系统边界和不变量，而不是微观规定所有实现方式；关键架构约束通过工具执行，而不只是写在文档中。这个取舍对 SDD 很有借鉴价值。OpenAI
   例如，导出功能的规范需要明确“只能导出当前用户有权访问的数据”“保留现有筛选语义”“下载时是否重新校验权限”。但不一定需要提前规定五个类名、每个私有函数的签名，以及尚未经过验证的设计模式。
   **实践重点：**反复练习审查规范中的每一段：它是在消除业务歧义、约束高风险决策、提供必要证据，还是仅仅把实现提前翻译成了自然语言？后者可能只是制造第二份需要维护的代码。
3. 不确定性管理：知道什么时候停止写规范，先去取证
   要深挖的，是区分“表达不清楚”和“事实还不知道”。
   两者的解决办法完全不同。前者可以通过澄清和评审改善；后者需要查资料、读代码、跑实验、访谈用户或做技术验证。把一个未知事实写得越来越具体，并不会让它变成事实。
   Spec Kit 当前的独立想法评估流程，也明确要求收集支持与反对证据、保留来源与置信度，并允许得出“需要澄清”或“不值得继续”的结论，而不是必然进入实现。GitHub Documentation
   例如，“第三方接口是否支持幂等”“现有数据库能否承受这类查询”“用户是否真的需要这个交互”，不能靠多轮架构师角色评审来确认。更合理的做法，是先设计一个最小验证任务，明确要观察什么、什么结果会推翻原方案。
   **实践重点：**让关键假设具有证据来源、验证方式和阻塞条件。学会在“澄清—探索—规范—实现”之间切换，而不是把 SDD 当作只能向前流动的流水线。
4. 存量系统改造：建立可信的变更基线
   要深挖的是如何让 AI 准确理解这次改动必须保留的行为。
   Spec Kit 的一个真实反馈记录了典型问题：在大型存量项目中，生成的方案看似合理，却缺少项目内部的架构知识，最终需要熟悉系统的人补充指导。当前官方指南因此建议，从有边界的增量变更开始，不要把“补齐全系统规范”作为采用 SDD 的前提。GitHub
   这里值得训练的，是把三件事分开：
   系统现在怎样运行、团队认可它应该怎样运行、本次准备改变哪一部分。
   它们并不总是一致。旧代码里可能有需要保留的兼容行为，也可能有恰好应该修复的错误。反向生成的文档，首先是对现状的描述，不能未经确认就升级为业务规范。
   **实践重点：**围绕变更区域收集现有接口、调用方、数据样例、测试、历史决策和兼容约束；先保护被认可的既有行为，再描述增量。持续提升“最小必要理解”的能力，而不是每次都让 AI 重新理解整个仓库。
5. 粒度控制：让规范、执行和验证形成同一个闭环
   要深挖的，不只是任务怎么拆，而是规范粒度、执行粒度和验收粒度是否匹配。
   一份规范覆盖整个系统，而每个 Agent 只修改几个文件，容易丢失全局约束；反过来，把规范拆成大量函数级指令，又可能造成跨任务关系碎片化。
   Anthropic 的早期长任务实验观察到，Agent 试图一次完成过多工作，会留下半成品和不清晰的交接状态；增量推进并留下可恢复的工作记录，是当时的重要改进方式。这里值得借鉴的是闭环与交接，而不是机械规定所有任务都采用同一个大小。Anthropic
   可以逐渐形成这样的分层：项目级约束相对稳定，能力级契约长期维护，本次变更描述增量，执行任务对应可验证的交付片段。
   例如，与其分别要求“完成全部前端”“完成全部后端”，可以先打通一个受限但完整的导出路径：提交任务、生成文件、授权下载。每次都能验证一个真实结果。
   **实践重点：**用“能否独立验证、能否审清差异、失败能否定位、中断能否恢复”判断粒度，而不是只用代码行数或预计工时判断。
6. 评审工程：研究什么评审真正增加了信息
   要深挖的，是评审的有效性，而不是评审轮数。
   一项发表于 InfoQ 的小规模试验，让五位评审者审查两个 AI 生成的服务。提供规范基线后，行为偏差的召回率没有显著提升，但问题更容易关联到具体要求；平均评审时间则从约 26.7 分钟增加到 48.4 分钟。它不是大规模生产结论，但说明了：可追溯性、缺陷发现能力和评审成本，是三个不同的指标。InfoQ
   因此，需要研究每轮评审究竟引入了什么：新的业务事实、独立的架构判断、可复现的反例，还是仅仅换一个角色重读同一份材料。
   我建议把高价值评审意见约束为：**违反了什么目标或约束，依据是什么，可能造成什么后果，是否必须修改。**把阻塞问题、待验证假设和个人偏好分开，避免所有意见都自动变成新的需求。
   **实践重点：**建立评审停止条件。关键风险已经处理，剩余取舍已经明确，就可以推进；如果争议来自事实不足，下一步应该取证，而不是继续增加“专家角色”。
7. 验证工程：让规范成为可以被证伪的验收契约
   要深挖的，是“什么证据足以证明实现符合要求”，而不是“AI 是否说测试通过”。
   这里至少要区分两种检查：规范是否表达了正确的业务意图，以及实现是否符合这份规范。代码与测试都忠实执行了一条错误假设，依然可能同时“通过”。
   Anthropic 的评测指南强调，根据任务组合程序化检查、模型评审和人工判断，并区分 Agent 的过程陈述与环境中的实际结果。例如，声称完成操作，与数据库里确实产生正确状态，不是一回事。Anthropic
   在 SDD 中，可以把关键要求连接到具体场景、验证方式和证据。例如，“不得跨租户导出”不仅需要正常用例，还需要跨租户访问、伪造资源标识、权限变化等反例；还可以在测试环境中故意移除权限校验，检查验收机制是否真的能够发现问题。
   同时要区分文档约束与执行约束：规范写“不得访问生产库”，不等于 Agent 已被禁止访问；这需要权限和环境控制。
   **实践重点：**持续校准验证器的漏检与误报，防止为了通过验收而悄悄降低标准。对于界面体验、模型效果等非纯确定性目标，还要维护样例、评价尺度和人工校准机制。
8. 规范演进：处理变更、发现、冲突与失效
   要深挖的，是第二次、第五次、第十次修改同一个功能时，哪些材料仍然值得信任。
   Spec Kit 当前明确区分不同维护方式：保留历史变更记录、维护长期规范，或允许代码与计划中的发现反向影响规范，再进行一致性整理。官方并没有要求所有团队采用同一种方式。OpenSpec 则通过分离当前规范与变更提案、在归档时合并增量，表达另一种维护思路。GitHub Documentation
   需要形成的判断是：这次发现改变的是业务目标、技术方案、任务安排，还是仅仅修复代码？变化应该传播到哪些材料？
   修复实现错误，不应该顺手把原有要求改成“错误行为也是允许的”；技术路径发生变化，也不必重新生成全部业务文档。已经失效的计划应该退出当前上下文，但仍有价值的决策理由需要保留。
   **实践重点：**明确规范的权威范围、版本、状态、负责人和替代关系。尤其区分“已批准”“已实现”“已发布”，不要让未来计划、当前生产行为与历史设计同时被当作现行事实。
9. 企业级协作与交付：从单仓库完成走向系统交付
   要深挖的，是规范怎样连接真实的组织分工和系统边界。
   一个开发者让 AI 扮演产品经理、架构师和测试工程师，并不等于已经获得这些角色的真实输入与授权。Hari Krishnan 的企业级实践文章专门讨论了这个问题：业务意图、跨仓库设计和仓库内执行任务应当分层组织，并与既有产品待办和协作流程连接。InfoQ
   例如，一个需求同时涉及前端、订单服务、权限服务和数据迁移，每个仓库各自“通过验收”，仍然不足以说明整个需求可以交付。
   需要明确的，不只是各仓库做什么，还包括：共同验收目标、接口契约版本、依赖关系、发布兼容性、迁移顺序、回滚条件，以及争议由谁决策。
   **实践重点：**让规范中的这些约束进入实际协作和交付机制。Agent 之间可以自主协调局部实现，但涉及需求变更、兼容性破坏或不可逆操作时，需要明确的升级与批准路径。不要把组织决策隐藏在某个 Agent 的一次推断里。
10. 效果评测与资产治理：把自己的 SDD 工作模式当作产品迭代
    要深挖的，是怎样证明这次流程调整真的比上次更好。
    Anthropic 在 2026 年的后续长任务实验中，采用逐项移除组件的方式判断哪些机制真正有用。随着模型能力变化，原先有价值的细粒度编排和频繁评估，在部分任务上变成了额外开销。这是一个很重要的启示：为旧模型设计的补偿机制，不应永久保留。Anthropic
    我建议保留一组真实需求样本，覆盖小修改、存量迭代、跨模块需求和高风险变更。比较轻量方案与完整 SDD 时，尽量保持模型、上下文、环境和验收口径一致，并进行多次试验，而不是凭一次成功案例判断。
    重点观察的不只是生成速度和 Token，还包括：人工投入、一次验收通过情况、返工、逃逸缺陷、规范维护负担，以及端到端交付时间。
    **实践重点：**每次只改变少量因素，例如减少一轮评审、调整规范粒度、替换验证器，再观察结果。Skill、模板、Hook 和规则都需要有存在理由与退出条件，不能只增不减。

方法论：

1. 流程裁剪：用“风险 × 不确定性”决定开发路径
   核心模型
   风险决定需要多强的控制，不确定性决定是否应该先探索。
   这两个变量不能混在一起。Prezi 的四团队工作坊反馈了部分任务流程过重、产物过量的问题；Allegro 的实践总结也认为，低复杂度任务不一定值得采用完整 SDD。这些经验支持按任务裁剪，但并没有给出普适分界线。Medium
   我建议使用以下两个轴：
   **横轴：关键决策的不确定性。**业务行为、技术可行性、现有系统约束是否已经明确？尚未解决的问题，是否可能推翻方案？
   **纵轴：变更失败的风险。**在现有控制措施下，一次合理可信的失败，会影响多少用户、数据和外部系统？是否容易发现、隔离和恢复？
   不确定性低：知道要做什么，也有可信实现路径 不确定性高：关键问题仍可能推翻方案
   风险低 **直接开发或轻量 SDD。**明确任务、边界与验收，直接实施，不生成完整文档链。 **探索优先。**先做可丢弃原型、技术验证或用户试用，学到东西后再决定是否形成规范。
   风险高 **契约型 SDD。**重点固化不变量、兼容要求、验证证据和发布条件，不必展开所有实现细节。 **分段承诺型 SDD。**先验证高影响假设，再批准关键方案，然后小步实现、分段验证。

这里的“不采用 SDD”，指不建立独立、持续维护的规范产物链，不是不说明需求、不评审、不测试。
怎么做
**先判断风险，不用代码量代替风险。**按钮文案修改通常可以直做；十行租户权限代码，也可能需要严格的契约和反例验证。跨服务调用不自动意味着高风险，但存在明确的兼容性破坏、不可逆数据变化或越权可能时，应升级控制强度。
**再判断未知，不用文档完整度代替确定性。**如果方案依赖“这个数据库查询一定能扛住”，但没有代表性数据和实验结果，那么即使技术方案写了二十页，仍然属于高不确定性。
**最后记录升级条件。**不只决定“这次走轻量流程”，还要写清楚：发现需要改公共 API、数据库结构或权限语义时，必须重新分流。路线不是一次性标签。
导出功能怎么用
一开始，数据规模未知、撤权后的下载行为也未确定，属于高风险、高不确定性。先完成代表性数据验证和权限语义澄清。
证据充分后，进入高风险、低不确定性：重点写清租户隔离、任务幂等、下载授权、失败恢复和发布条件，而不是再补一份更长的需求文档。
**停止条件：**没有可能推翻当前关键方案的未处理假设，且高风险要求已有可信的验证路径。
最重要的启发：不要把“需要更多证据”，误判成“需要更多规范”。2. 规范表达：用“约束分层＋双解检验”逼近最小充分规范
核心模型
锁定正确性的边界，保留实现方式的自由。
OpenAI 的工程实践强调，集中约束系统边界和不变量，在边界内允许 Agent 自主选择实现；Matt Wynne 的 Example Mapping 则强调，规则需要具体例子支撑，同时显式保留尚未回答的问题。OpenAI
可以据此把规范分为三层：
层次 应该写什么 AI 的自由度
目标与不变量 为什么做、什么结果算正确、什么行为绝不能发生 不得擅自修改，需要需求或风险负责人确认
外部契约 输入输出、状态变化、兼容要求、失败语义、性能约束 可以提出修改，但不能静默改变
内部实现选择 类划分、内部算法、私有函数、局部组织方式 在满足前两层与仓库约束的前提下自主决定

现有事实提供证据链接；未知事项进入假设清单。不要把事实、要求、建议、猜测，都写成同一种“必须”。
怎么做
第一步：把抽象词变成可以区分对错的行为。
“导出要安全可靠”没有足够约束力。可以改为：
普通用户只能导出本租户且处于其授权范围内的数据。
用户被撤权后发起的新下载请求必须被拒绝，即使下载地址在撤权前已经生成。
同一导出任务重试，不得产生重复的业务副作用。

这些要求约束的是业务结果，而不是类名和设计模式。
第二步：执行“双解检验”。
让 AI 分别提出两个“都声称符合规范”的合理解释，先不要实现代码，只比较它们的可观察行为。
例如：
解释 A：提交导出时鉴权，下载时不再鉴权。
解释 B：提交和下载分别鉴权。

如果两个解释都能从规范中说通，但业务只接受其中一个，规范就存在需要消除的歧义。
反过来，如果差异只是采用不同的内部类结构，而业务结果、可维护性和架构约束都满足，就不必强行统一。
第三步：执行“删减检验”。
逐段问：删掉这段，会不会允许某种不可接受的行为？会不会丢失关键决策依据或必要上下文入口？
不会产生这些后果的内容，可以删除、下沉到参考材料，或者留给实现阶段决定。
边界与停止条件
“双解检验”是发现歧义的方法，不是两次解释一致就证明规范完整。它应优先用于权限、计费、状态流转、兼容性等高代价分歧。
**停止条件：**关键要求有规则、有例子、有验证方式；剩余差异主要属于允许的实现自由，而不是业务解释分歧。
最重要的启发：规范的充分性，看它排除了多少错误解释；不看它提前写出了多少代码细节。3. 不确定性管理：用“假设映射＋最小取证”替代反复空想
核心模型
先找出“必须成立但缺乏证据”的假设，再寻找最便宜的有效取证方式。
Teresa Torres 介绍的假设检验实践，强调测试单个关键假设，而不是先构建整个产品；她引用 David Bland 的假设映射方法，用“重要性”和“已有证据”识别优先验证对象。Product Talk
这里先做一次问题分诊：
尚未解决的问题 正确动作
大家不知道业务到底要什么 找有决策权的人澄清、取舍
同一句话存在不同理解 用具体场景和反例消除歧义
不知道某件事在现实中是否成立 查证、观测、技术验证或用户研究
要求已经明确，但 AI 没有执行 改上下文、执行约束或验证机制

不能用更多 Review，代替第三类问题所需的真实证据。
怎么做
先反问方案：要让它成立，哪些事情必须是真的？
例如，异步导出方案可能依赖：
“查询结果能在分页过程中保持所需的一致性”“失败后可以安全重试”“下载地址能够满足撤权策略”。
然后优先处理同时满足以下条件的假设：**一旦不成立就会改变重要决策、现有证据薄弱、验证成本相对可控。**不必把每条假设都打成一个看似精确的分数。
再为每个关键假设定义一个最小取证任务。
任务至少需要说明：
要验证的命题、现有证据、失败会影响的决策、取证方法、通过与失败的判定、结果适用的版本和环境。

通过标准应来自业务或系统约束，不能看到实验结果后再临时降低。
最后只提升证据支持的那部分结论。
一次小数据量测试成功，只能支持该范围内的结论；不能直接升级成“百万级数据没有问题”。实验结果必须带适用边界。
导出功能怎么用
假设是：
已生成的下载地址，仍然能够阻止被撤权用户的新下载请求。

最小验证不需要先实现整个导出系统。只要在隔离环境中完成“生成地址—撤权—再次请求”的链路。
若实测不能满足要求，下一步是改变下载架构，或者由业务负责人明确接受另一种授权语义；不是让 AI 在技术方案中继续论证原方案“原则上可行”。
**停止条件：**证据已经足以选择方案；剩余未知被隔离在可逆范围内，或者有明确的风险接受与后续验证安排。
最重要的启发：探索应为具体决策准备必要的信息。4. 存量系统改造：用“行为基线＋授权差量”控制变更
核心模型
新旧实现的可观察差异，应当落在获批变更范围内。
EPAM 的存量项目复盘强调，需要向 Agent 提供真实架构、接口样例和具体集成点，否则容易产生通用但不适配的方案。Spec Kit 官方指南也建议从有边界的变更开始，而不是先补齐整个旧系统的规范。EPAM
我建议建立三种边界：
边界 回答的问题
保留行为 哪些现有行为已被认可，本次必须保持？
授权差量 哪些行为本次允许或要求改变？
变更禁区 哪些接口、数据结构、依赖或副作用不得被顺带修改？

注意：观测到的旧行为，不自动等于应当保留的正确行为。
怎么做
先沿变更路径理解系统，而不是全仓库泛读。
从真实入口开始，追踪：
入口 → 身份与权限 → 业务规则 → 数据和副作用 → 下游调用方。
收集相关代码、接口协议、代表性数据、已有测试和历史决策。每项关键结论尽量有出处，避免 AI 根据目录名称猜测架构。
再对现有行为进行分类。
已认可的行为进入保留基线；确认要修复的问题进入授权差量；无法判断对错的行为标记为待确认。
例如，旧导出文件将空值输出为空字符串。如果下游确实依赖它，应保留；如果只是历史偶然行为，需确认是否值得继续承担兼容成本。
然后建立行为围栏。
对保留行为补充有针对性的回归测试；对授权差量编写新验收；对禁区设置变更检查或必要的审查。
能够进行新旧实现差异测试时，使用同一组脱敏输入比较结果，并解释每个重要差异。涉及发送消息、收费、写外部系统等副作用时，回放必须隔离。
导出功能怎么用
新增异步导出，可以允许增加任务查询接口；但现有订单查询的筛选语义、JSON 响应结构和普通用户权限边界，应当保持。
Agent 顺手“统一分页接口”“优化全部鉴权代码”，即使代码看起来更优雅，也超出了授权差量，需要重新评估。
**停止条件：**在已覆盖的场景中，重要差异都能对应到明确批准的变化；尚未覆盖的兼容风险被显式记录。
最重要的启发：存量项目中，要让 AI 准确区分“必须改变”和“必须不变”的行为。5. 粒度控制：用“纵向切片＋三重预算”确定执行单元
核心模型
选择能够被完整理解、独立验证、清楚恢复的最大闭环，而不是机械追求最小任务。
Anthropic 早期长任务实验发现，一次尝试完成过多工作会留下半成品和不清晰的交接状态；增量推进、保留清晰工作记录，是其改进机制之一。但这不意味着所有模型、所有任务都必须按相同大小切分。Anthropic
我建议用三个预算判断一个任务是否过大：
预算 判断问题 超标信号
理解预算 Agent 能否获得当前任务必需的规则、上下文和依赖？ 反复遗忘约束、不断重新搜索、混淆不同方案
反馈预算 本轮结束后，能否判断具体完成了什么？ 只能说“代码写了很多”，无法独立验证结果
恢复预算 失败或中断后，能否定位、隔离并继续？ 必须重读全部历史，多个未完成改动纠缠在一起

这些预算需要结合模型和仓库校准，不宜规定成统一的 Token 数、文件数或工时。
怎么做
先按用户能力拆纵向切片，再按依赖拆执行任务。
不要只有“完成前端”“完成后端”“最后联调”。先找到一个能够贯穿真实路径的有限能力。
导出功能可以先打通：提交任务—执行导出—查看状态—授权下载，限制数据规模和开放范围，但权限等核心不变量不能延期。
随后再分别增强大数据量处理、失败恢复、配额控制等能力。每一步都能增加可验证的价值。
每个执行单元只需要一个紧凑工作包：
输入基线 → 本次变化 → 必须保持的约束 → 验收入口 → 交接状态
交接状态应记录实际提交、执行过的检查、结果和未解决问题，而不是只有“已完成”的自述。
根据反馈调整粒度。
频繁遗漏上下文，就缩小工作包或改善上下文装配；每个微小任务都重复初始化和评审，则合并任务；失败难定位，就缩短未验证变更的累积长度。
边界与停止条件
**不要求“一份 Spec＝一个任务＝一个测试”。**合理关系是：每个任务知道自己实现了哪些契约，每个重要契约有对应验收。
便宜的局部检查可以高频执行，昂贵的端到端或性能验证放在相关风险节点，不必每修改一行都全量运行。
最重要的启发：任务粒度由理解、反馈和恢复能力共同决定。6. 评审工程：用“主张—反例—证据—裁决”替代无限多轮 Review
核心模型
评审的单位应该是高风险主张，而不是整份文档；评审的价值应该是新增证据，而不是新增意见。
Nitin Garg 的小规模评审研究发现，提供规范基线改善了问题归因，但没有显示缺陷召回的显著提升，并增加了评审耗时。它不能证明规范评审无效，却提醒我们：可追溯、发现问题和评审成本需要分别观察。InfoQ
可以把评审组织为：
关键主张 → 构造反例 → 查找证据 → 做出裁决 → 更新受影响产物
怎么做
首先让作者显式列出高风险主张。
例如：
重试不会重复产生导出结果。
撤权后无法发起新的有效下载。
新旧版本可以在发布窗口内共存。

这些主张比“方案整体是否合理”更容易审查。
评审者针对主张寻找能够推翻它的场景。
评审指令应给出以下具体要求。
找出可能违反该主张的执行路径；说明依赖什么条件；给出代码、协议、实验或业务事实作为证据。

先做独立判断，再阅读作者的辩护理由，是值得尝试的防锚定做法；但不能把更换角色提示词视为真正的信息独立。
将评审结果分流，而不是全部变成修改任务。
评审结果 下一步
有证据支持的缺陷 修改并补充对应验证
重要但证据不足的疑点 转成取证任务
多种方案都成立的取舍 由责任人裁决并记录理由
风格偏好或非目标优化 默认不阻塞，避免扩大范围

相同要求、相同失败路径的问题应合并，防止不同 Agent 换个说法反复提出。
导出功能怎么用
评审者指出：“下载地址足够随机”不能回答“撤权后是否仍能使用旧地址”。
这时，真正有价值的下一步是执行撤权后的新请求验证，而不是再启动一个“安全专家 Agent”发表意见。
Anthropic 也报告过，独立评估 Agent 仍可能过于宽松，需要对照实际问题持续校准；因此，角色分离只是起点，证据和校准才是关键。Anthropic
**停止条件：**重要主张获得充分支持，不可接受的风险已经关闭，剩余取舍已有明确责任人。连续讨论没有新证据时，转向实验或决策，而不是继续增加 Review 轮次。
最重要的启发：评审为关键决定提供依据。7. 验证工程：用“契约证据链＋反向挑战”验证实现，也验证验证器
核心模型
规范负责定义正确，验证器负责区分对错，执行环境负责产生证据。三者不能相互代替。
Anthropic 的评测实践区分了 Agent 的过程陈述与环境中的实际结果，并建议组合程序化、模型和人工评审。模型说“操作成功”，不等于系统状态已经正确。Anthropic
建议建立这样的证据链：
业务依据 → 规范要求 → 正例与反例 → 验证方式 → 执行结果
怎么做
先确定预期结果从哪里来。
验收标准应来自业务确认、可信协议、已有兼容契约或经校准的评价标准，不能只从新生成的代码反推。
同一个模型生成实现和测试并非天然不可行；真正的问题是：二者是否共同依赖了同一个未经验证的错误假设。
然后按要求选择验证方式，而不是按工具补数量。
关键要求 必须覆盖的挑战场景 需要观察的实际证据
不跨租户导出 用户尝试访问其他租户的任务或文件 未返回其他租户的数据，权限判定符合要求
撤权后拒绝新下载 先获取地址，撤权后再发起请求 新请求被拒绝，而不只是页面隐藏按钮
重试不重复副作用 执行到关键中间状态后失败，再重试 任务状态、最终产物和外部副作用符合幂等契约
满足性能约束 指定数据分布、并发与资源限制 实测延迟、资源占用和错误情况，而不是估算

前端体验可以结合真实交互、状态断言和人工认可的视觉基线；模型效果类需求需要样本集与校准后的评分标准，不能硬套纯二元测试。模型评审本身也需要人工校准。Anthropic
最后反向挑战验证器。
在隔离环境中，故意删除租户过滤、跳过下载鉴权，或者制造重复执行条件。检查验收是否真的失败。
这与变异测试的思路一致：有意改变实现，观察测试能否检测到变化。需要排除等价变异等情况，不能把所有“存活变异”都机械视为真实漏洞。stryker-mutator.io
边界与停止条件
Agent 可以增加测试，但不能为了通过验收，未经确认就放宽业务标准或删除独立验收。
对安全、数据完整性等硬要求，不应让“其他项目分数很高”抵消失败。验证器反向挑战成功也不意味着系统已被完全证明正确，只能增强对已覆盖风险的信心。
**停止条件：**重要要求有可信预期、适合的验证方式和可复核证据；针对核心风险植入的代表性错误能够被拦截。
最重要的启发：测试通过之前，先确认测试有能力失败。8. 规范演进：用“目标基线—变更集—发布快照”维护可信状态
核心模型
规范一致性要求每份材料的状态和版本清晰可辨。
Spec Kit 当前明确区分双向回流、历史变更记录和长期维护规范等策略，并指出各自存在漂移、重复或决策理由丢失的风险。Thoughtworks 的 SPDD 实践则将规范性提示资产纳入版本控制和持续同步。GitHub Documentation
我建议分清三个对象：
**目标基线：**当前批准的业务契约，说明系统应该怎样运行。
**变更集：**相对于某个基线，本次新增、修改或删除什么，以及为什么。
**发布快照：**某个环境实际部署的代码、配置、契约版本及其验证记录。
因此：
目标规范 v3 已批准，不等于生产环境已经运行 v3。
变更已归档，也不等于功能已经发布。

怎么做
发生变化时，先判断应该改哪一层。
变化类型 优先修改 必须检查的传播范围
业务行为改变 需求契约与验收标准 设计、实现、测试、兼容与发布安排
技术路径改变，业务目标不变 技术决策与执行计划 性能、可靠性、运维和相关测试
实现违背既定要求 代码与回归用例 通常不修改业务要求
只是表达或格式调整 对应文档 不自动重跑完整开发流程

建立少量高价值关联。
关键要求关联到相应设计决策、接口、测试和变更记录即可。可以使用要求编号、链接和测试标签，不必先建设复杂的知识图谱。
当一条要求变化，沿这些关系检查受影响对象。测试结果也应关联被测提交与环境，不能让旧版本的“通过”继续为新代码背书。
显式处理并发变更。
两个分支修改同一条授权规则时，即使 Git 没有文本冲突，也可能发生语义冲突。应基于共同基线比较意图，再更新集成后的规范和验收。
导出功能怎么用
原规则是“地址在有效期内可下载”，新规则是“每次新下载请求都检查当前权限”。
需要更新的不只是页面文案，还包括授权契约、下载方案、相关接口、撤权反例和发布兼容性。单独更新 spec.md，并不能完成变更传播。
**停止条件：**能够回答“当前批准了什么、生产部署了什么、二者有哪些差异、哪些证据对应哪个版本”。
最重要的启发：维护时应通过版本关系区分目标、事实和历史。9. 企业级协作：用“契约依赖图＋兼容发布”连接多仓库交付
核心模型
按业务目标统一验收，按契约边界分配工作，按版本兼容关系安排发布。
Hari Krishnan 的企业级 SDD 实践文章，将业务意图、跨仓库设计和仓库内执行任务分开：业务目标保持可见，技术任务落在对应仓库，依赖关系由架构上下文约束。InfoQ
这张图表达以下契约和依赖关系。
节点代表交付工作包；边代表明确的接口、数据或版本依赖；每个节点都有验收责任。
怎么做
先定义系统级完成条件，再往各仓库拆。
例如，用户能够发起导出、看到真实状态、在授权下下载结果，并且故障恢复满足约定。这是共同目标。
前端、API、Worker 各自完成代码，只能证明局部进展，不能自动推出整个功能完成。
每条跨边界依赖都写成契约。
除请求响应结构外，还应明确关键的错误语义、幂等责任、权限责任、兼容版本和负责人。
例如，“API 服务检查过权限，所以 Worker 不需要处理授权上下文”就是一个需要明确裁决的边界问题，不能让两个 Agent 各自猜测。
契约明确后再并行。
能够并行的前提，是依赖已固定或有受控替代，并且最终如何验证真实集成已经明确。Mock 通过不代表真实 Provider 符合契约。
Pact 的版本矩阵与 can-i-deploy 展示了一种可复用机制：根据已经执行的消费者—提供者契约验证，判断候选版本能否与目标环境中的版本组合。但它不能替代没有写入契约的业务、安全或性能验收。Pact Docs
最后设计兼容发布，而不只是代码合并顺序。
典型路线是：
增加兼容能力 → 迁移或切换调用方 → 验证与观察 → 移除旧能力。
这对应 Parallel Change 的扩展、迁移、收缩模式；它的价值是降低同步升级要求，但代价是过渡期需要维护新旧两套行为，因此必须有退出计划。martinfowler.com
导出功能怎么用
先部署兼容的数据库结构和消费者，再部署生产新任务的能力；功能开关仍保持关闭。完成集成验证后开放功能，观察稳定后再移除过渡实现。
具体顺序取决于契约，不应把这个示例顺序当作所有项目的固定模板。
**停止条件：**不仅各仓库验收通过，目标版本组合也通过集成验证，并有可执行的开放、回退或补偿安排。

核心模型
先约束质量和风险，再优化总交付成本；每个新增流程都需要证明价值，每个旧流程都允许被删除。

怎么做
第一步：建立可比较的真实任务样本。
从历史需求中选取不同类型的任务，保存原始需求、仓库快照、必要上下文、环境和验收口径。
同一个任务，比较轻量流程、当前 SDD，以及移除某一环节后的 SDD。尽量固定模型版本、初始条件和预算，使用独立会话，避免把前一次答案直接泄漏给后一次。
**终点必须相同。**不能让完整 SDD 的验收更宽松，也不能把它多花的人工澄清和评审时间排除在成本之外。
第二步：看端到端指标，不只看编码速度。
评价维度 重点观察
质量与风险 关键契约违背、验收遗漏、后续逃逸缺陷
人工投入 澄清、规范审阅、评审、修复和维护所用时间
交付效率 从任务开始到满足共同验收口径的总耗时，以及异常拖长情况
运行与维护成本 模型、环境成本，以及规范和流程资产的维护负担

多次运行，观察失败分布，不只展示最好的一次。任务差异较大时，优先比较同任务的配对结果，而不是直接混合平均。
第三步：逐项消融。
例如只减少一轮技术方案 Review，或只取消函数级任务拆解，其余条件保持一致。
如果减少成本且没有观察到质量退化，它是一个可继续验证的简化候选；但小样本中的“没看到问题”，不能证明低频严重风险不存在。
第四步：让经验进入合适的资产，而不是全部追加到提示词。
发现的问题 更合适的沉淀位置
缺少真实项目事实 文档、上下文入口、检索机制
反复遗漏某类业务步骤 场景化 Skill 或模板
稳定、可自动判定的不变量 测试、静态检查或 CI 门禁
某次独特的架构取舍 决策记录，不直接升级为通用规则
旧模型的特定弱点 带适用条件的补偿机制，并在升级后复测

严重风险不需要等到反复发生才治理；但不能因为一次局部失败，就给所有任务永久增加一大段通用指令。
