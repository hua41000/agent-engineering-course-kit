01

流程裁剪：所有需求都要走完整的 SDD 流程吗？

低风险做轻，高风险做严；低复杂度直接做，高复杂度分阶段做。
风险决定控制强度，复杂度决定交付方式。

风险程度：做错会造成多大影响？高风险要明确契约，加强 Review、安全检查和测试验收。

复杂度：涉及多少模块与依赖？高复杂度要做技术设计、拆解任务，分阶段实施并集成验证。

遇到不确定性：需求或技术路径不清楚时，先澄清或探索，将其作为流程中的待解决问题。

以下用电商 DataAgent 的四类任务举例，按给定范围判断风险与复杂度。

02

AI写的代码还需要人工Review吗？

为什么审 → 哪些要审 → 怎么审：把人工投入留给风险与核心认知。
01 / WHY

模型写得流畅，不等于实现可靠

01 · 误判业务语义

代码改得合理，业务算错了

Python · 错误示例
# 业务：起止日期都计费
# 原逻辑正确
days = (end_date - start_date).days + 1

# AI 当成 off-by-one 修复
days = (end_date - start_date).days
# 错误：每笔订单少计一天费用
02 · 核心功能缺失

接口返回成功，核心流程没执行

Python · 错误示例
@app.post("/orders/export")
def export_orders(request):
    validate(request)
    # TODO: 查询订单并生成 CSV
    return {"status": "success",
            "csv": ""}
# 错误：有订单时仍导出空内容
03 · 迎合测试破坏约束

测试通过了，权限边界被删了

Python · 错误示例
def get_order(user, order_id):
    order = db.get_order(order_id)
    # AI 为消除测试报错删掉校验：
    # if not can_access(user, order):
    #     raise PermissionDenied()
    return order
# 错误：其他店铺的订单也能读取
04 · 架构与代码质量退化

局部功能能跑，模块边界被绕过

Python · 错误示例
@app.post("/orders/{id}/refund")
def refund(id):
    # Controller 绕过领域服务直接改库
    db.execute(
        "UPDATE orders SET status = ? "
        "WHERE id = ?", ("REFUNDED", id))
# 错误：跳过状态约束和退款领域事件
05 · 生产级可靠性不足

单次测试正确，并发请求出错

Python · 错误示例
def purchase(product_id):
    product = db.get_product(product_id)
    if product.stock > 0:
        # 两个请求都可能读到 stock = 1
        product.stock -= 1
        db.save(product)
        return create_order(product_id)
# 错误：缺少并发控制，可能超卖
06 · 验证与 Review 失真

测试全绿、评审说好，证据仍不够

Python · 错误示例
def test_payment():
    response = client.post("/pay",
        json={"order_id": 123})
    assert response.status_code == 200
    # 未核对扣款、订单状态、支付流水

# AI Review：“有测试，支付流程正确”
# 错误：仅凭 200 无法证明支付完成

六类模式覆盖“做错、做坏、验错”。代码为简化教学反例，用于说明问题，不代表真实项目缺陷或模型错误率。

人工审查不能全省的两个根本原因

风险控制

核心模块错误，影响面巨大

  • 认证授权：默认拒绝改为允许 → 越权。
  • 支付退款：验签放宽 → 伪造回调。
  • 数据库：Schema 迁移锁表 → 生产故障。
  • 消息：重试不幂等 → 重复记账。
  • 发布：Flag 默认开启 → 未验证功能全量暴露。
人类认知掌控

系统不能变成“无人区”

  • 认知：掌握核心实体、状态、依赖与边界。
  • 判断：识别 AI 对架构长期演进的破坏。
  • 应急：故障时有人懂调用链、能修复。
  • 成长：审关键实现，持续提升工程能力。
  • 责任：核心模块始终有人类 Owner。
两者取并集风险审查拦截缺陷；认知审查维持理解。
02 / WHAT

低风险、可验证、可逆的代码交给自动化

可免人工逐行审查

这些工作交给 AI 与自动化

  • README、普通注释、非敏感文案
  • 局部 UI 样式（视觉回归已通过）
  • 机械式 DTO / Mapper 样板代码
  • 源契约已审的生成代码
  • 纯格式化、无语义修改
自动放行的前提

质量门槛仍然保留

  • 变更范围明确，不触及关键路径
  • CI、静态检查、对应测试通过
  • 不涉及权限、密钥、生产配置
  • 可追踪、可回滚
  • 定期抽样复审放行结果

“不用审”指免人工逐行阅读；测试与质量门槛照常执行。按变更语义判断，不按代码行数机械判断。

重点审查：高风险路径 + 认知锚点

需要审的类型重点内容示例
核心实体 / 类型抽象Entity、Value Object、聚合根、类型约束Order / Money / Refund
领域模型骨架状态机、不变量、领域事件、业务规则退款状态迁移表
代码结构 / 架构边界模块职责、分层、依赖方向、公共抽象Controller → Domain → Repository
核心接口契约API、消息 Schema、Policy 接口权限策略、Kafka 事件协议
高风险执行路径资金、权限、迁移、并发、回滚支付验签、数据库回填
团队知识薄弱区AI 大量生成但尚无人理解的核心模块新计费引擎、调度内核
人持续掌控即使测试全绿，核心架构和领域骨架也要由模块 Owner 持续掌握。
03 / HOW

设计预审 → AI 验收 → 上线前关键复核

阶段 1 · 技术方案 Review

/my-create-design

默认产出要求：生成核心架构代码片段，供人工预审。

  • 模块结构与依赖
  • 核心实体 / 类型抽象
  • 领域模型骨架 / 状态机
  • 关键接口 / 不变量

审“系统应该长成什么样”。

实现后 · AI 辅助测试验收

AI Coding + Verify

先执行并修复：

  • 单元测试：规则与边界
  • 集成测试：接口与依赖
  • E2E 测试：关键用户路径
  • 必要的并发 / 故障测试

留存真实 CI 与测试证据。

阶段 2 · 上线前人工 Review

/my-code-review

AI Review 后输出：

  • 人工必审代码清单
  • 文件 / 函数 / 风险理由
  • 关键失败场景与测试证据
  • 实现偏离设计骨架的地方

人审关键变更，决定放行。

两个人工审查阶段设计时审关键抽象；实现验收后审关键偏差。中间的 AI 测试是强制质量门槛。

以上按附件定义目标工作流。当前仓库实际评审入口为 /my-review-code；核心代码片段与人工必审清单尚未设为 Skill 默认产出，使用时需明确要求。

03

技术债治理：AI Coding 怎么避免技术债累积？

每次迭代都在增加理解、修改、验证和协调成本时，就要治理持续累积的技术债。
01 / 方法论

事前立约束，事中审增量，事后查存量

02 / 典型债务

四类会持续增加后续修改成本的债务

01架构边界侵蚀

局部需求，逐渐变成跨团队联动

Python · 技术债示例
# orders/service.py：穿透其他模块内部存储
from inventory.repository import StockRow
from billing.repository import LedgerRow

def cancel_order(order):
    StockRow.increment(order.sku, order.quantity)
    LedgerRow.update(order.id, status="REVERSED")

持续成本：内部模型一变，订单团队也要跟改。
治理落点：事前约定公开接口与依赖方向；事中拦截跨模块直写。

02数据与接口契约漂移

同一字段换了含义，历史数据持续混存

Python · 技术债示例
# 旧契约：amount 单位为元
save_order({"amount": "19.90"})

# 新迭代改为分，未迁移、未增加单位标识
save_order({"amount": 1990})
# 报表仍把所有 amount 按元汇总

持续成本：修复需追溯历史数据、消费者与兼容窗口。
治理落点：设计 Review 核对单位与迁移；存量分析定位语义分叉。

03业务规则重复与分叉

同一规则复制多份，修改只覆盖一部分

Python · 技术债示例
# 统一政策已经调整为 14 天
def refundable_in_app(order):
    return order.age_days <= 14

# 客服入口仍保留旧副本
def refundable_in_support(order):
    return order.age_days <= 7

持续成本：每次调整政策都要找齐副本，遗漏会反复出现。
治理落点：增量 Review 检查复用；独立分析后统一同一业务规则。

04回归验证失真

用实现生成预期，错误被测试一起接受

Python · 技术债示例
def test_checkout_total():
    order = make_order()
    expected = calculate_total(order)
    actual = checkout(order)["total"]
    assert actual == expected
# checkout 也调用 calculate_total
# 若这是唯一金额测试，算错时两边一起错

持续成本：测试失去保护作用，后续只能靠人工回归与补丁。
治理落点：代码 Review 查断言独立性；存量分析补业务已知值与反例。

其他典型债务：团队认知与责任断层、权限与安全边界碎片化、临时补丁与历史分支堆积、错误抽象与过度设计、故障恢复与可观测性欠账、依赖与交付环境漂移、性能与资源预算透支、有效文档与 Agent 上下文失真。

代码为简化教学示例。缺陷一旦形成持续绕路、重复排查和人工兜底，便会不断增加维护成本。
