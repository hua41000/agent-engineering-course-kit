你的两点修正非常关键，我也更倾向于这种工程实践：

第一，\*\*历史 SDD 文档应该作为历史研发档案，而不是需要持续同步的系统事实。\*\*需求验收后，文档完成使命。未来 AI Coding 应优先理解当前代码、测试和有效的架构约束，只有必要时才检索历史 SDD 文档。

第二，\*\*Code Review 的强度不能只看代码变更本身，还要看它所处的业务模块，以及失败的影响范围。\*\*一个只有三行的支付逻辑修改，可能比新增三千行内部管理页面更值得人工审查。

基于这两个原则，我重新整理四套适合企业级 SDD 实践的方法论。每一套都包含核心判断、执行方法、具体案例和适合沉淀的工程资产。

# 一、Code Review 到底能不能省？

## 核心观点

Code Review 可以大幅减少，但不能一刀切地取消。应该根据业务重要性、变更风险和验证能力，决定人类介入程度。

传统 Code Review 经常要求工程师阅读所有代码 Diff。但 AI Coding 时代，代码产出速度显著提高，这种方式可能成为交付瓶颈。

更合理的方式，是把 Code Review 从默认的全量人工检查，转变为风险驱动的分级审查。

## 方法论：业务重要性 × 变更风险，验证能力作为放行门槛

Code Review 分级决策矩阵

低业务重要性 · 高变更风险

重点 Review

关注复杂实现、跨模块影响、数据迁移和回滚

高业务重要性 · 高变更风险

严格 Review

架构、核心逻辑、安全边界、关键 Diff，必要时双人复核

低业务重要性 · 低变更风险

自动 Review

静态检查、AI Review、自动化测试，人工按需抽查

高业务重要性 · 低变更风险

定向 Review

即使 Diff 很小，也审查核心不变量和失败影响

纵轴为业务重要性及失败影响，横轴为变更风险。矩阵是建议的初始分流规则，而非固定行业标准。

这里有三个关键判断。

1\. 业务重要性：出问题的代价有多大？

例如支付、权限、订单结算、核心交易链路，即使改动很小，也可能产生严重影响。

2\. 变更风险：这次修改有多容易引入问题？

包括跨模块影响、复杂状态变化、并发处理、数据迁移、兼容性、可逆性等。

3\. 验证能力：我们是否有足够可靠的手段发现错误？

这是独立的放行门槛，而不是第三个需要机械打分的坐标轴。缺少可信验证时，即使处于低风险象限，也不应轻易自动放行。

### 实际案例：支付服务中的三行修改

假设 AI 为修复优惠券问题，修改了支付金额计算：

```
# 原逻辑payable = total - discount# AI 修改后payable = max(0, total - discount)
```

只有一行变化，单元测试也可能全部通过。

但它属于核心资金模块，需要人工重点检查：

- 是否允许优惠券金额超过订单金额？
- 订单应当被拒绝，还是允许产生零元支付？
- 退款、分账、财务对账是否依赖原有金额语义？
- 是否会掩盖本应暴露的上游计算错误？

这里需要审查 AI 是否擅自改变了资金业务规则。

### 落地建议

在 PR 阶段，由 AI 自动生成一份精简的 Review Brief：

- 变更涉及哪些业务模块？
- 是否触及关键业务不变量？
- 哪些关键设计决策发生了变化？
- 哪些 Diff 需要人类重点关注？
- 哪些验证已经执行，哪些风险尚未覆盖？

工程师根据这份摘要定位关键代码，但必须能追溯到实际 Diff 和验证结果。

结论：不是所有代码都值得人工 Review，但所有高代价的工程决策都必须处于有效控制之下。

# 二、AI Coding 怎么避免技术债累积？

## 核心观点

不要试图消灭所有技术债，而要防止 AI 在每次增量开发中持续破坏已有架构。

AI Coding 中一种典型问题是：

每次任务都能通过验收，但每次实现都增加一点重复、耦合和临时逻辑。随着需求不断叠加，系统越来越难维护。

这是一种局部任务成功、长期工程退化的现象。

## 方法论：架构护栏 + 增量技术债检查 + 触发式重构

### 第一层：架构护栏，约束 AI 不要随意破坏已有设计

在仓库级 `AGENTS.md` 中记录稳定、重要的架构规则。

例如：

```
## Architecture Constraints

- 订单金额计算只能通过 PricingService 完成。
- Controller 不得直接访问数据库。
- 跨模块调用必须通过已定义的 Service 接口。
- 优先复用已有业务抽象，不得随意复制核心规则。
- 新增公共依赖或改变模块边界时，必须先说明理由。
```

这些是可以长期复用的工程约束，不需要每次 SDD 都重新生成。

其中能够机器检查的依赖规则，最好进一步下沉到静态分析或 CI 中，不能只依赖模型记住。

### 第二层：每次交付进行增量技术债检查

重点检查本次变更是否引入了新的架构问题。

可以重点检查：

| 检查项   | 需要发现的问题                       |
| -------- | ------------------------------------ |
| 重复实现 | 是否复制了已有业务规则？             |
| 架构边界 | 是否新增了不合理的跨模块依赖？       |
| 抽象设计 | 是否出现无必要的抽象或过度设计？     |
| 复杂度   | 是否显著增加了分支、状态或隐式耦合？ |
| 可测试性 | 新增逻辑是否难以隔离和验证？         |

这里尤其需要避免 AI 把所有代码风格问题都当成技术债。真正值得关注的是对未来修改成本、故障风险和系统理解成本有实际影响的问题。

### 第三层：建立触发式重构机制

满足以下条件时再考虑重构。

例如：

- 同一业务规则出现多处重复。
- 一个简单需求需要修改越来越多模块。
- 某模块反复出现同类回归缺陷。
- 当前实现明显突破了已有架构边界。
- 继续叠加需求会显著增加复杂度或风险。

重构应有明确范围、收益假设和回归保护，避免借机进行无关的大规模改造。

### 实际案例：订单优惠计算逻辑逐渐失控

假设最初系统只有普通订单，统一通过 `PricingService` 计算价格。

后来 AI 连续完成多个需求：

第一次增加会员优惠，在 Controller 中增加条件分支。

第二次增加满减活动，在订单服务中复制一套计算逻辑。

第三次增加渠道折扣，在支付服务中又实现一套规则。

每次功能测试都通过，但三个模块开始维护不同的金额计算逻辑。

下一次调整优惠叠加规则时，AI 可能需要同时修改三个地方，并且很容易遗漏其中一个。

正确的治理方式是：

事前：明确价格计算必须经过统一的业务服务。

事中：AI Review 发现本次新增了重复的金额计算逻辑，阻止继续扩散。

事后：如果历史重复已经存在，单独安排一次有回归保护的收敛重构。

不应该等到系统出现大量故障之后，才让 AI 全面重写价格模块。

结论：技术债治理的关键，是让 AI 在完成本次需求时，不持续损害下一次需求的开发效率。

# 三、如何解决 Spec 和代码不同步的问题？

## 核心观点

不要追求历史 SDD 文档与代码持续同步。需求验收完成后，历史 SDD 文档应当归档，默认不参与未来的代码理解和开发决策。

我认为这是一个非常重要的工程取舍。

很多 SDD 方法容易把规范视为需要长期维护的系统真相，但企业级系统会经历大量 Bug 修复、重构、性能优化和需求迭代。

如果每次代码变化都同步所有历史 PRD、技术方案和任务文档，不仅维护成本巨大，还可能产生大量内容相互矛盾的文档。

更合理的方式是：

区分长期有效的工程知识与一次性需求过程资产。

## 方法论：长期知识维护 + 历史 SDD 归档 + 按需检索

### 第一层：长期知识，持续维护

这类内容描述当前系统中仍然有效、未来开发需要遵守的规则。

例如：

- `AGENTS.md`：仓库级开发约束与知识入口。
- `docs/architecture/`：当前架构和关键模块边界。
- `docs/contracts/`：长期有效的接口或业务契约。
- 测试代码、API Schema、数据库 Schema：可执行或可检查的系统契约。

这些内容应根据实际变化维护。

但也不需要把所有实现细节都转写成文档。

### 第二层：历史 SDD 文档，验收后冻结

例如：

```
specs/
  archive/
    2026-08-order-export/
      prd.md
      design.md
      tasks.md
      test-plan.md
```

这些文档记录的是：

当时为什么做、准备怎么做、有哪些约束和设计考虑。

它们不再承诺描述系统当前状态。

验收后可以补充归档日期、关联 PR、交付版本和最终验收结果，然后冻结。

未来代码变化，不要求反向同步历史文档。

### 第三层：通过 AGENTS.md 明确历史文档的读取策略

这是最值得固化的一点。

建议在仓库的 `AGENTS.md` 中增加：

## Historical SDD Documents

`specs/archive/` contains historical SDD artifacts from completed development tasks.

### Default Rules

- Historical SDD documents are archived records, not authoritative descriptions of the current system.
- Do not search, read, or load `specs/archive/` by default during code exploration, implementation, or debugging.
- Prefer current source code, tests, schemas, and maintained architecture documentation when understanding the system.
- Do not update historical SDD documents to match subsequent code changes.

### When to Read

Read relevant historical SDD documents only when:

1. The user explicitly requests historical requirements or design decisions.
2. The rationale behind an existing implementation cannot be determined from current code and maintained documentation.
3. A new requirement is closely related to a previous feature, and its historical design may provide useful context.
4. Investigating a regression requires understanding the original behavior or constraints.

### Usage Rules

- Read only the relevant historical documents, not the entire archive.
- Treat historical content as context, not as current truth.
- Verify important historical assumptions against current code and tests.
- If historical documentation conflicts with current implementation, investigate the discrepancy rather than automatically changing either.

这段约束有两个价值：

\*\*减少上下文污染。\*\*防止 AI 把已经过时的技术方案当作当前架构。

\*\*减少维护负担。\*\*历史 SDD 文档不再需要随着代码持续演进。

### 实际案例：历史订单导出方案误导新需求

假设 2025 年开发订单导出功能时，技术方案采用：

> API 服务同步查询数据库，直接生成 Excel 文件。

这个方案已经归档。

2026 年，系统经过性能优化，改为：

> API 提交任务，Worker 异步生成文件，对象存储提供下载。

现在需要增加“导出任务取消”功能。

如果 AI 默认扫描历史 SDD 文档，很可能依据旧方案设计同步取消逻辑，甚至提出已经不适用的改造建议。

正确流程应该是：

1. 优先读取当前导出模块代码、任务状态机和测试。
2. 理解当前异步执行机制。
3. 只有需要了解当初某项业务规则的来源时，才定向检索历史 SDD。
4. 读取后验证相关假设是否仍然有效。

历史文档可以解释为什么曾经这样设计，但不能直接回答系统现在如何工作。

### 一个需要保留的例外

如果某条历史需求中包含仍然有效、且未来必须遵守的重要业务不变量，就不应该只把它留在历史档案里。

例如：

> 导出文件不得包含当前租户以外的数据。

这条规则应该沉淀到当前业务契约、权限测试或长期工程约束中。

归档的是研发过程，不是放弃仍然有效的关键约束。

结论：历史 SDD 文档应该成为可检索的研发档案，而不是持续同步的第二份代码。

# 四、SDD 中工程师要介入最后的验收吗？何时何法？

## 核心观点

工程师应该掌握最终交付质量，但介入的重点是关键验收标准、风险与证据，而不是亲自重复执行 AI 已经可靠完成的全部测试。

一个常见误区是：

让 AI 生成 Spec、编写代码、生成测试，再由同一个 AI 宣布“所有测试通过，任务完成”。

这里存在一个潜在风险：

AI 既定义了成功标准，又负责执行，最后还负责判断自己是否成功。

即使 AI 没有刻意放宽标准，也可能因为需求理解偏差，让代码和测试共同验证一个错误假设。

## 方法论：前置验收设计 + 分层自动验证 + 风险驱动人工放行

### 第一阶段：实现前，工程师确认验收契约

这是最值得投入人工判断的阶段。

工程师不一定亲自编写所有测试用例，但应该确认：

- 核心业务场景是否覆盖。
- 高风险反例是否覆盖。
- 哪些质量要求必须满足。
- 哪些验证必须依赖真实环境。
- 什么条件下可以自动放行，什么条件下必须人工确认。

尤其需要区分：

功能验收标准由业务需求决定，不能由 AI 根据自己实现的代码反向定义。

### 第二阶段：实现中，AI 自主验证，异常时升级

正常情况下，AI 可以自主完成：

单元测试、接口测试、集成测试、静态检查、必要的端到端测试，以及失败后的定位和修复。

但出现以下情况时，应主动请求工程师介入：

- 发现原有 Spec 存在重要歧义。
- 需要改变已批准的架构或业务契约。
- 自动化验证无法判断某个关键结果。
- 修复问题需要降低原有验收标准。
- 涉及不可逆的数据操作或高风险生产变更。

这样可以让工程师只在真正需要判断和授权的地方介入。

### 第三阶段：交付前，按风险进行证据验收

| 任务风险           | 工程师验收方式                       |
| ------------------ | ------------------------------------ |
| 低风险、验证充分   | 自动放行或抽样检查                   |
| 常规业务需求       | 检查关键验收结果、异常和重要实现变化 |
| 核心业务需求       | 定向检查关键代码、核心场景和集成验证 |
| 高风险或不可逆变更 | 独立验证、人工审批、灰度与回滚审查   |

其中，业务验收与技术放行也应分开。工程师负责技术质量判断，业务负责人负责确认需求是否真正满足。

### 实际案例：用户权限系统改造

假设需求是：

> 新增部门管理员角色，只能管理本部门成员。

AI 完成了代码和测试，并报告全部通过。

但是工程师发现，AI 的测试主要覆盖：

- 部门管理员可以查看本部门用户。
- 部门管理员可以修改本部门用户。
- 普通用户没有管理员权限。

这些都是正向测试。

但缺少最关键的反向场景：

部门管理员是否可以通过修改请求中的用户 ID，操作其他部门成员？

如果没有这条反例，即使全部测试通过，也不能证明权限
